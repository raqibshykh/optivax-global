# Phase 5 — Business Logic Audit Report

**Scope:** every ERP module's workflow correctness — HR, Payroll, Attendance, Projects, Tasks, Clients, Invoices, Payments, Budget, Marketing, Sales, IT Support, Production, Notifications, Calendar, Automation, Files, Email Marketing. Verified against evidence in the actual frontend (`src/`) and backend (`wordpress-backend/optivax-erp-backend/`) code, not assumptions. No live WP+MySQL instance was available in this environment — every PHP change was verified with `php -l` (syntax only); every frontend change was verified with a full `npm run build` (`tsc -b && vite build`), which passed cleanly (zero errors) after every fix in this phase.

---

## Fixes applied

### 1. Stripe checkout was a fake payment confirmation
- **Root cause:** `StripeCheckoutForm` in `src/pages/Client/Billing.tsx` already rendered a real `<CardElement>` and called `useStripe()`/`useElements()`, but discarded both return values — `handleSubmit` just ran a `setTimeout` and called `onSuccess` unconditionally, regardless of whether a card was even entered.
- **Why broken:** a client could "pay" an invoice with no card details, no charge, and no real Stripe transaction — the invoice would be marked paid in the ledger for money that was never actually collected.
- **How fixed:** rewrote `handleSubmit` to create a real payment intent (`POST /saas/v1/create-payment-intent`), call `stripe.confirmCardPayment()` with the actual `CardElement`, and only invoke `onSuccess` after Stripe confirms `paymentIntent.status === "succeeded"`. Failure paths (declined card, missing Stripe/Elements instance) now show a real error toast instead of silently succeeding.
- **Files modified:** `src/pages/Client/Billing.tsx`.
- **How to test:** attempt checkout with a Stripe test card (e.g. `4242 4242 4242 4242` for success, `4000 0000 0000 0002` for a decline) and confirm the invoice only moves to paid/partially-paid on an actual successful charge.

### 2. Paid invoices could still be edited; payments could exceed the outstanding balance
- **Root cause:** `InvoiceController::update()` (PHP) had no restriction on which fields could be changed once an invoice had payment history, and `stripeConfirm()` didn't re-validate the requested amount against the invoice's own remaining balance before rolling it into the ledger.
- **Why broken:** an invoice already partially or fully paid could have its `amount`/`status` silently rewritten, desyncing the payment ledger from reality; a forged or buggy `stripeConfirm` call could push `amountPaid` past the invoice total or drive `remainingBalance` negative.
- **How fixed:** added a `FINANCIAL_FIELDS` guard in `update()` — once an invoice's status is anything other than `pending`/`overdue`, edits to `amount`/`amountPaid`/`remainingBalance`/`status` are rejected with a 409 (metadata fields like description/dates/notes remain freely editable). Added a balance check in `stripeConfirm()` that rejects any amount exceeding the invoice's outstanding balance before the transaction runs.
- **Files modified:** `wordpress-backend/optivax-erp-backend/controllers/InvoiceController.php`.
- **How to test:** `PUT /saas/v1/invoices/update` with `{id, amount: <new value>}` against a `partially_paid`/`paid` invoice should return 409; `POST /saas/v1/invoices/stripe-confirm` with an amount greater than the invoice's outstanding balance should return a 422 validation error.

### 3. Leave-approval → payroll deduction divergence (two unrelated leave stores)
- **Root cause:** the codebase independently grew two leave-request features with different shapes (`HRLeaveRequest`: `userId`/lowercase `status`, served by `/saas/v1/leave-requests`; `LeaveRequest`: `employeeId`/capitalized `status`, served by `/saas/v1/hr/employee-leave-requests`). `countApprovedLeaveDaysInMonth()` in `payrollService.ts` only queried the first store.
- **Why broken:** an employee whose leave was approved through the "employee self-service" flow (`Client/Profile.tsx` submission, reviewed via `HRPanel.tsx`/`SuperAdminPanel.tsx`) had that leave silently ignored by payroll — no unpaid-leave deduction applied even though the leave was genuinely approved.
- **How fixed:** `countApprovedLeaveDaysInMonth()` now queries both stores in parallel and sums correctly-cased/correctly-keyed approved leave days from each, without unifying the underlying data model (a much larger, riskier change not required to fix the actual bug). Applied the same two-store merge to `Payroll.tsx`'s separate `countApprovedLeaves()`/auto-sync helper, which had the identical single-store gap.
- **Files modified:** `src/services/payrollService.ts`, `src/pages/HR/Payroll.tsx`.

### 4. Three divergent payroll-calculation engines producing different net-pay figures
Three separate pages independently compute payroll for the same employee/month, and two of them had real, fixable defects:

- **`SalarySlips.tsx` / `BulkSalarySlips.tsx` (the "official" slip generator, using `computeStrictDeductions()`):** both hardcoded `monthlyAttendance: null` when calling `computeStrictDeductions()`, so absent-day, half-day, and late-arrival deductions were always zero regardless of actual attendance records — only unpaid-leave and advance-salary deductions ever applied.
  - **Fix:** both pages now fetch real attendance data via `AttendanceService.getYearData()` and compute a real `MonthlyReport` via `computeMonthlyReport()`, passing `{absentDays, halfDays, lateArrivals}` into `computeStrictDeductions()` instead of `null`.
  - **Files modified:** `src/pages/HR/SalarySlips.tsx`, `src/pages/HR/BulkSalarySlips.tsx`.

- **`AttendancePayroll.tsx` (a live payroll-reporting view, using `computePayrollEntry()`):** its base-salary lookup read `localStorage.getItem("optivax_employee_extra")` — a key nothing in the current codebase writes to anymore (the real per-employee salary override was migrated to a backend-backed `EmployeeExtraService` in an earlier phase, but this one read site was never updated). Every employee's reported base salary silently fell back to a generic role-based default, disagreeing with their actual configured salary shown everywhere else.
  - **Fix:** `computePayrollEntry()` now takes an `employeeExtra` parameter (additive, defaults to `{}` — its one caller was updated, so this is not a breaking change) instead of reading `localStorage` internally. `AttendancePayroll.tsx` fetches real data via `EmployeeExtraService.getAll()` and passes it in.
  - **Files modified:** `src/domain/attendance/calculations.ts`, `src/pages/HR/AttendancePayroll.tsx`.

- **`Payroll.tsx` (a manual paid/unpaid ledger with a simpler formula):** this page is not a duplicate of the above — it's a genuinely different workflow (HR manually types a `leavesTaken` count and marks salary Paid/Unpaid, with an optional one-click "sync from HR records" button; no half-day/late-arrival/advance-recovery logic at all). Its leave-count sync had the same two-store gap fixed in item 3. Its simpler formula is an intentional design difference for a lighter-weight tracking page, not a bug — unifying it with `computeStrictDeductions()` would remove HR's manual-override capability and was left alone.

### 5. Duplicate task creation on double-submit
- **Root cause:** `Tasks.tsx`'s `handleAdd` had no in-flight guard — a slow network response plus a user re-clicking "Add Task" (nothing visually changes until the request resolves) would fire `TaskService.create()` twice, creating two identical tasks.
- **How fixed:** added an `isCreatingTask` state, checked at the top of `handleAdd` and used to disable the submit button (showing "Adding…") for the duration of the request.
- **Files modified:** `src/pages/Common/Tasks.tsx`.

### 6. No server-side sanity check on payroll figures
- **Root cause:** `PayrollController.php` is a near-pure storage passthrough — every gross/deduction/net figure is computed on the frontend and stored exactly as submitted, with no server-side recomputation.
- **Why broken:** a buggy client or a forged direct request could submit a salary slip with `netSalary` disconnected from `basicSalary`, and the backend would accept it verbatim. A full server-side port of the deduction engine (attendance/leave/advance-recovery cross-domain lookups) was judged too large and risky to build and verify without a live database in this environment.
- **How fixed:** added the one invariant that's always true under the company's actual payroll policy (gross salary equals basic salary — no allowances/bonuses are ever added — so net pay can never legitimately exceed basic salary) as a cheap boundary check in both `createSalarySlip()` and `bulkSaveSalarySlips()`. Rejects `netSalary > basicSalary` or negative `netSalary` with a validation error.
- **Files modified:** `wordpress-backend/optivax-erp-backend/controllers/PayrollController.php`.

### 7. IT ticket status could be changed with no transition rules
- **Root cause:** `PUT /saas/v1/it/tickets/update` was wired straight to the generic `BaseCrudController::updateByBodyIdHandler()` — the `status` enum was only validated on ticket *creation*, never on update, so a request could move a ticket from `closed` back to `open`, or set any status at any time, with no check at all.
- **How fixed:** added a route-level guard: when a status change is requested, it's validated against the same enum used at creation, and a closed ticket cannot be moved to any other status (a fresh ticket must be filed instead). This is enforced at the API layer, not just hidden via button visibility in the UI (which was already the case, but provided no real protection against a direct API call).
- **Files modified:** `wordpress-backend/optivax-erp-backend/routes/ItSupportRoutes.php`.
- **How to test:** `PUT /saas/v1/it/tickets/update` with `{id: <a closed ticket>, status: "open"}` should return 409.

### 8. Redundant/duplicate task-completion notifications; unused dedicated helper
- **Root cause:** `Tasks.tsx`'s `moveTask()` fired both `notifyTaskStatusChanged()` (which already notifies department admins generically and logs a `TASK_UPDATED` audit entry) and a separate ad-hoc local `notifyAdminsOfCompletion()` function that duplicated the admin-notification logic with raw `NotificationService.create()` calls — while the codebase's own purpose-built `notifyTaskCompleted()` helper (correct recipient targeting, dedicated `TASK_COMPLETED` audit action) sat completely unused.
- **How fixed:** removed the ad-hoc `notifyAdminsOfCompletion` function and its duplicate notification path; `moveTask()` now calls the existing `notifyTaskCompleted()` helper directly, giving completion events their own accurate audit-log action instead of relying solely on the generic status-change one, and removing the redundant second notification admins previously received for the same event.
- **Files modified:** `src/pages/Common/Tasks.tsx`.

## Confirmed working, no fix needed

- **Notifications module** (`src/services/notificationHelpers.ts`, ~60 helper functions): verified wired at real call sites across Tasks, Billing/Invoices, IT Support tickets (create/assign/resolve/escalate/close/reopen all call `notifyTicketStatusChanged`, which itself notifies the requester and logs an audit entry), and more. Broad coverage confirmed; no other dead/unused notify helpers found besides the one addressed in item 8.
- **Audit logging:** most mutation logging is bundled inside the `notify*()` helpers, so wherever a notify call fires, an audit entry is created alongside it. Spot-checked HR/Payroll/Budget/Invoices/Projects/Tasks — the one confirmed silent gap (task completion, item 8) is fixed.
- **File uploads** (`src/hooks/useFiles.ts`, `wordpress-backend/.../uploads/UploadService.php`): a real multipart upload path exists and works — `POST /saas/v1/files/create` calls `wp_handle_upload()` and stores the file in the WordPress media library when a real file is attached. The frontend hook currently only ever sends a local `URL.createObjectURL()` blob reference (never real file bytes), so uploaded "files" only resolve for the browser session that created them — but this is a frontend integration gap against an already-working backend, not a missing feature. See "Explicitly not fixed" below.
- **Attendance calendar:** `AttendanceCalendar.tsx` is fully wired to real `AttendanceService` data, no dead mock data found.
- **Email/SMTP infrastructure:** a real `MailService` exists (`wp_mail()`-backed, SMTP-configured) and is actively used for password-reset and welcome emails, plus an `EmailQueueWorker` cron for async notification email delivery. This infrastructure exists and works — it's just not connected to the Email Marketing campaigns feature (see below).

## Explicitly not fixed — documented, with reasoning

- **Budget `usedAmount` is never incremented anywhere in the codebase.** `MemberAllocation.usedAmount` is only ever set to `0` (new allocation) or preserved unchanged from the prior value (`idx >= 0 ? all[idx].usedAmount : 0` in `BudgetManagement.tsx`) — there is no code path anywhere that increases it in response to actual spending. Every "Used"/"Remaining"/"Utilization %" figure across `BudgetManagement.tsx`, `MyBudget.tsx`, and the department/company budget stats is permanently frozen at 0-used/100%-remaining. This is a genuine, complete workflow gap, not a small bug — fixing it correctly requires designing a new "record spend/expense" mechanism (e.g., rolling up campaign task `budgetUsed` into a member's allocation, or a manual expense-entry feature), and there's no existing spec or UI hint for which of those is the intended design. Inventing that business rule unprompted risked being wrong; flagging it precisely here is the safer choice.
- **Commission `amount` has no auto-calculation from the existing Type/Rate fields.** `Commissions.tsx`'s form has a "Commission Type" (Percentage/Fixed) and "Rate/Value" field, but "Commission Amount ($)" is a fully separate, manually-typed, required field — nothing computes it as `value% × <some deal amount>`. There is no "deal/sale amount" field anywhere in the form to compute a percentage against, so the Percentage option is currently decorative. A real fix requires adding a new input (a deal/sale amount) whose correct source (a linked won deal? an invoice? a manual figure?) isn't specified anywhere in the code — same reasoning as above, documented rather than guessed.
- **Email Marketing campaigns cannot actually send email.** Confirmed via the backend: `EmailMarketingController.php`'s `createCampaign`/`updateCampaign` are pure generic CRUD wrappers with no send action anywhere — `Campaigns.tsx`'s "Send Now" button just sets `{status: "sent", stats: {sent: 100, opened: 0, clicked: 0}}` (hardcoded fake stats) with no call to the mailer at all. The backend's real `MailService`/`EmailQueueWorker` infrastructure (used for password-reset/welcome/notification emails) is never invoked for campaigns. Building real send-to-recipient-list logic (subscriber iteration, template rendering, `MailService::queue()` calls, real open/click stats) is a substantial feature addition, not a contained bug fix — flagged for a dedicated follow-up rather than attempted here.
- **Automation module execution cannot be verified from the frontend.** `useAutomation.ts`/`automationService.ts` and the Email Automation page are pure CRUD/toggle UI — enabling a workflow just flips a database flag; there is no client-side trigger evaluation or scheduler. Whether anything actually executes these rules depends entirely on a backend cron/worker that could not be verified without a live WP instance in this environment. Not claimed as fixed or broken — flagged as unverified.
- **Content Calendar is a standalone feature**, not unified with Tasks/Leave/Attendance calendars (each domain has its own calendar view backed by its own service). This is a design characteristic, not a defect — no single "calendar of record" was ever built, and none of the phase's source material implied one should exist.
- **File visibility enforcement on listing (staff-facing) was not changed.** `Files.tsx` captures a visibility option (private/department/specific/project-team/client) on upload but the frontend's `FileService.getAll()` path used for internal staff doesn't filter by it (only the client-facing `getByClientId()` path is scoped). Whether this is actually enforced server-side could not be confirmed without a live backend to test against — flagged rather than assumed safe or unsafe.
